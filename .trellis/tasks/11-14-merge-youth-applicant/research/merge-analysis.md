### Risks

- Resolving the merge by 'take officer' or 'take applicant' per conflicted file cannot work for api.ts, StatusBadge.tsx or App.tsx: each needs a hand-written combined version, and the 3-way conflict hunks in api.ts will be large and interleaved (officer changed 65/685 lines vs base, applicant 4/528).
- skeleton.css, demo/README.md and docs/DEVELOPMENT.md auto-merge without a conflict marker, so they will not appear in a conflict list; skeleton.css must be forced back to the officer version or the officer loading skeletons lose their styling with no build error.
- The 15 silently dropped files produce no conflict either. 14 of them are imported, so tsc fails loudly if they are missing, but phone.test.ts has no importer and would vanish unnoticed.
- Both app-shell.css versions style the same unscoped `.shell*` selectors differently; loading both in one bundle changes one side's header unless the rules are scoped (applicant already has an `.app-shell--applicant` scope for part of its rules).
- OfficerConsole deliberately nulls its state for /apply paths and ApplyFlow treats officer params as removed entries; a combined App.tsx needs a path-based switch, and these guards were written assuming the other half does not exist.
- The reconciled-union proof is a typecheck only. `npm run build`, oxlint, the 18 scenario scripts and pytest were not run on any combined tree, and README states a 500KB bundle-size warning baseline that a combined bundle may cross.
- Officer api.ts imports mock-data.ts (1,500+ lines of synthetic rows) at module level, so in a combined api.ts the applicant bundle also pulls in officer mock data unless split.
- The doc baselines disagree by design: officer docs quote 1,264 engine tests at e449c55 while applicant docs are still the base text (260 tests, old repository name); whichever is kept needs rewriting for the merged repository.
